## 适配决策与原理

### 1. 为什么 JEI 与 REI 不需要额外代码

Deadly Monsters 没有引入任何自定义配方类型（`RecipeType`）、配方序列化器（`RecipeSerializer`）、专用合成容器或特殊工作台。模组内包含的 17 个合成配方全部基于 Minecraft 原生标准 Crafting 配方格式构建。

JEI 与 REI 本身具备直接读取原版注册物品与标准合成配方的完备能力。在此场景下额外引入专用的适配插件类，仅会徒增编译依赖、耦合风险与维护成本。保持纯净的原生数据格式，是跨配方查看器最具韧性的兼容方式。

### 2. Jade 信息显示

本模组的所有方块与实体均通过标准的 Minecraft / NeoForge 注册系统声明。Jade 的基础显示逻辑（如方块名称、实体血量与基本属性）能够直接通过原版元数据解析，无需 Deadly Monsters 编写专属的 Client Provider。

当前模组内不包含复杂的能量网络、流体储罐、合成进度条或私有 BlockEntity 状态。因此，无需为了形式上的兼容而引入空壳插件。后续若扩展自定义机制并需要展示额外 Tooltip 时，再行接入 Jade API。

### 3. EMI 生态现状与跟进原则

截至当前评估周期，EMI 官方在 Modrinth 与 GitHub 上尚未发布针对 Minecraft 26.2 的正式或测试构建，因此目前缺乏可在 26.2 环境下进行实机联合测试的运行依赖。

本仓库坚决反对针对尚未发布的目标版本盲目引入旧版 API、反射探测或空壳桥接代码。Deadly Monsters 继续严格维护标准数据结构，待 EMI 官方 26.2 构建就绪后，直接按照 [测试清单.md](测试清单.md) 执行联调复验即可。

## 兼容性设计原则

* **不引入非必要硬依赖**：所有外部生态交互均以可选或原生数据驱动为主。
* **原生标准优先**：优先采用 Minecraft 标准注册、数据组件与配方格式，避免生态碎片化。
* **按需扩展**：仅当真实出现自定义配方类型、复杂机器交互或高阶 Tooltip 诉求时，才编写最小化的专属适配代码。
* **杜绝空壳代码**：兼容层必须服务于真实的用户交互价值，而非仅为了在外部模组列表中堆砌名称。
